# コミット規約

Claude Code・Codex共通で[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)に従う。
この規約はメッセージの作り方を定めるもので、commit/pushの許可を与えない。

## 形式

```text
<type>[optional scope][!]: 日本語の説明

任意の本文

任意のフッター
```

`[]`は省略可能な部分を表す記法で、実際のscopeは`(設定対象)`のように括弧で囲む。
コロンの後には半角スペースを置く。説明・本文・フッターの説明文は日本語を既定とし、技術識別子・コマンド・設定キー・原文引用は保つ。
ユーザーが別の言語を明示した場合はその指定に従う。type、scope内の技術識別子、`BREAKING CHANGE`などの構文上の印は英語のままにする。

## typeの選択

- `feat`: 機能追加。
- `fix`: 不具合修正。
- `docs`: ドキュメントのみの変更。
- `refactor`: 機能追加や不具合修正を伴わないコードの整理。
- `perf`: 性能改善。
- `test`: テストの追加・修正。
- `build` / `ci`: ビルド・依存関係 / CI設定の変更。
- `style`: 動作を変えない書式の変更。
- `chore`: 上記に当てはまらない保守作業。

`feat`と`fix`以外のtypeは、この配布物で使う目安であり仕様の必須語彙ではない。
scopeは変更対象が伝わる場合だけ付ける。変更内容に合うtypeを選び、実際の差分を短く説明する。

## 破壊的変更と例

互換性を壊す変更には、type/scope直後の`!`またはフッターの`BREAKING CHANGE: 日本語の説明`を必ず付ける。どのtypeでも破壊的変更を示せる。
`!`だけで示す場合も、説明文で何が変わり互換性を壊すかを伝える。本文・フッターはヘッダーと空行で区切る。

正しい例:

```text
feat(settings): 日本語の既定設定を追加
fix(config): 設定ファイルの読込パスを修正
docs: 配布手順を説明
refactor(api)!: 廃止済みの認証引数を削除
```

フッターで破壊的変更を示す例:

```text
feat(config): 設定ファイルの形式を更新

BREAKING CHANGE: 旧形式の設定ファイルは読み込めないため、新形式へ移行する
```

修正が必要な例:

- `日本語設定を追加`: typeがない。`feat: 日本語設定を追加`へ修正する。
- `feat: add Japanese language setting`: 別言語の明示指定がなければ、`feat: 日本語の既定設定を追加`へ修正する。
- `refactor(api): 廃止済みの認証引数を削除`: 実際に互換性を壊す変更なら、`refactor(api)!: 廃止済みの認証引数を削除`などへ修正する。

コミット前に差分とメッセージを照合し、type欠落・説明文の言語・破壊的変更の印の漏れを直す。
これは作成時の指示であり、hookやcommitlintによる強制ではない。既存履歴は書き換えない。
